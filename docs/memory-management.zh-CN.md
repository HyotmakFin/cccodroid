# 内存：怎么判断、怎么排查、内存管家怎么工作

[English](memory-management.md)

手机上跑重活（逐帧渲染、大规模并行编译、长视频转码），最怕跑到一半整个应用被系统杀掉。这篇记的是我们在真机上踩出来的经验，以及内存管家（`cc-mem`）为什么这样设计。

## 1. 先看对数字

`free` 显示的「已用」会吓人：在一台 15 GB 的平板上，它报过「已用 11 GB」。拆开一看：

| 项 | 大小 | 说明 |
|---|---|---|
| 进程真正占着的（AnonPages） | 2.6 GB | |
| 文件缓存 | 5.9 GB | 读过的文件留在内存里加速，要用时内核直接丢掉 |
| 可用（MemAvailable） | 10.8 GB | 这才是还能用多少 |

判断内存够不够，看 `/proc/meminfo` 的 **MemAvailable**。想知道谁占着，用 `priv 'dumpsys meminfo'`，末尾的 `Total RAM` 一段最直观：真正在用多少、多少能腾出来（空闲 + 内核缓存 + 后台缓存应用）。

## 2. 被杀了，先查是谁杀的

安卓内存告急时，低内存杀手（lmkd）会**按应用整体**杀。重活是应用的子进程，它把内存吃光，连应用和正在进行的对话一起带走。事后可以这样查：

```sh
priv 'logcat -d -b events' | grep -E 'killinfo|am_mem_factor|am_kill'
```

- `am_mem_factor` 变大：系统进入了内存紧张状态；
- 同一秒里一大批应用的服务被安排重启（`am_schedule_service_restart`）：整机被打爆、一锅端；
- `killinfo` 里能看到被杀那一刻的空闲内存和文件缓存还剩多少。

## 3. 先怀疑自己有没有漏

我们那次把会话打断两次的元凶，不是后台应用，是自己的渲染脚本：resvg 的 WebAssembly 版本，每渲一帧都 new 一个对象，用完不 `free()`。WebAssembly 里的内存不归 JavaScript 的垃圾回收管，于是每帧漏一张约 8 MB 的画布。6 个进程并行，合计能涨到 20 GB 左右。

修好之后，每个进程稳定在约 135 MB。8 个进程 66 秒渲完 86 秒的 1080p 片子，整机可用内存始终在 10 GB 左右。

经验：**放开并发之前，先单进程跑一会儿，盯着 RSS 涨不涨。** WebAssembly、原生绑定（sharp、canvas 之类）的对象，都要查有没有 `free` / `dispose`。

## 4. 内存管家（cc-mem）

自己不漏了，后台那些「上划关掉又自己活过来」的应用仍然在抢内存。日志里能直接看到它们是怎么回来的：自己的守护服务、内置的第三方推送、名字就叫「保活」的定时任务，还有被别的应用查询数据时顺带唤醒。

内存管家默认关闭，在设置里打开。它做三件事：

- `cc-mem status`：内存账，以及哪些应用可以停、哪些受保护、为什么；
- `cc-mem clear`：停掉白名单以外的后台应用；
- `cc-mem run -- 命令`：开跑前清场并做一次系统内存压缩，跑的过程中每 2 秒巡视一次，谁复活就再停谁，结束后报告。

### 保护谁

不写死包名，直接问系统：

1. **系统自己的分档**：`dumpsys activity lru` 给每个进程标了重要程度。前台、可见、可感知、常驻的（分屏的另一半、挂着前台通知的代理和音乐、输入法）一律不动，只考虑「服务」和「缓存」档。
2. **自动识别**：当前桌面、输入法、无障碍服务、VPN、WebView 提供者、Shizuku、本应用、系统核心组件。
3. **用户的白名单**。
4. **依赖关系**（最容易漏，见下一节）。

### 停一个包，会连带杀掉谁

这是实测踩出来的。安卓停掉一个包时，**会连带杀掉所有加载过这个包的进程**：

- 停了 WebView 这个包，所有用 WebView 显示界面的应用都被杀了，包括 cccodroid 自己；
- 停了联想日历，系统的分屏服务也跟着死了，因为它加载了日历的组件。

还有一类：一个应用通过 ContentProvider 稳定地连着另一个应用的数据，提供方一死，安卓会把连着它的客户端一起杀掉。

所以内存管家会读 `dumpsys activity processes` 里每个进程的 `packageList`、`packageDependencies` 和稳定的 provider 连接。凡是**不停的进程**离不开的包，也划进保护名单。多保护一个包，就多一批进程活下来，它们的依赖也要保护，所以反复迭代，直到名单不再变化。

### 其他细节

- **进程名不等于包名。** `com.huawei.hwid.core` 只是进程名，所属的包是 `com.huawei.hwid`。拿进程名去 `am force-stop`，什么都不会发生，而且不报错。要以 `packageList` 为准。
- **两档力度**：日常清理用 `am stop-app`（保留应用的定时任务，之后可能被唤醒）；`run` 用 `am force-stop`（取消定时任务，用户再打开之前都起不来）。
- **丢文件缓存做不到，也不必做。** `/proc/sys/vm/drop_caches` 要 root，shell 身份写入被拒。文件缓存本来就是可回收的，内核要用时直接丢，提前清空反而让后面的程序重新从闪存读。
- **反复复活的应用**可以 `cc-mem tame 包名` 长期限制后台（`am set-bg-restriction-level … restricted`），`cc-mem untame` 恢复原来的级别。
